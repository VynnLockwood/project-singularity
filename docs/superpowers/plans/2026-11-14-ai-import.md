# AI Import Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Import tab where an editor drops in an `.xlsx`/`.csv` file and writes a prompt. A Profiler → Matcher → Designer → Critic relay produces a checked scripts mapping, which the editor reviews and submits as one gated change.

**Architecture:**
- A new Django app `intake` turns the file into sources, profiles them locally, and matches them against the search index (the local e5 model) and existing rows (the duplicates engine).
- It asks the chat model once per round for a mapping JSON, and checks that mapping with the existing `scripts.validate`.
- The checked plan becomes a pg_dump-style script that the existing scripts submit path turns into a Change.
- Runs execute as a background child process like `scripts.jobs`, and the page polls.

**Tech Stack:** Django 5, psycopg 3, openpyxl, pgvector, the `singularity_engine` duplicates engine; Next.js 15, React, vitest.

**Spec:** `docs/superpowers/specs/2026-11-14-ai-import-design.md`

## Global Constraints

- Editors and approvers only (`user.can_edit`). Viewers get 403, and the nav item has `minRole: "editor"`.
- Nothing is applied without the existing submit → approval flow. Intake never runs DDL or DML itself.
- Only profiles (headers, types, stats, at most `sampleValues` = 5 sample values per column, each cut to 80 chars) go to the chat model, never whole rows.
- Accepted files: `.xlsx`, `.csv`. CSV is UTF-8 (BOM allowed), falling back to TIS-620 (`cp874`).
- File cap `import.maxFileBytes` = 52428800. Row and op caps come from `limits.maxScriptRows` / `limits.maxOpsPerScript`.
- Settings block `import` with defaults: `model: ""`, `maxFileBytes: 52428800`, `sampleValues: 5`, `maxRounds: 3`, `rowMatch: true`.
- A typed column only when EVERY non-empty value parses as that type; otherwise text. Thai digits / Buddhist-era years are converted only when the whole column parses that way.
- Exact business-key matches: skipped and listed. Name matches: "maybe", loaded unless the person ticks them.
- Recipe fingerprint = sorted, trimmed, lower-cased header names (no file or sheet name), per database.
- Runs and their files expire after 24 hours unless submitted. One open run per user per database.
- Run states: `profiling`, `matching`, `designing`, `waiting_for_answer`, `checking`, `ready`, `failed`, `submitted`.
- The `apiKey` is never logged, stored or echoed. It is passed only to `chat.providers.complete`.
- New `api/` routes are WEB_ONLY in `tests/test_mcp_parity.py`, with a reason.

## Review Focus

1. Codes with leading zeros (`00123`, a 13-digit tax ID, a phone number) → stay text with the zeros. Numeric Excel cells for a code column are not turned into `123` or `1.23E+12` (Task 3 `test_leading_zero_codes_stay_text`).
2. A header not on row 1, blank or duplicate headers, merged title cells above the header → the first non-empty row is the header, `column_3` / `name_2` style names, and nothing crashes (Task 2 `test_header_detection_edge_cases`).
3. The Designer returns JSON that does not parse, or maps a column that does not exist → one parse retry. The Critic reports the unknown column, and the run never reaches `ready` with an invalid mapping (Task 7 `test_bad_designer_output_never_ready`).
4. A recipe whose target column was dropped since approval → the drift is reported in the thread and the Designer repairs it. The recipe is not applied blindly (Task 7 `test_recipe_drift_is_repaired`).
5. Formula cells with no cached value, date cells, and Excel booleans → read as empty / ISO date / `true`/`false`, not as the formula text or a datetime repr (Task 2 `test_cell_values`).

### Task 5: Script writer

**Interfaces:**
- Consumes: Tasks 2–4.
- Produces: `write(sources: list[Source], profiles: list[dict], plan: dict, schema: str) -> bytes`. The result is pg_dump-style UTF-8 text:

- Produces: `apply_filter(rows, headers, filter) -> list[int]`, the kept row indexes (used by the Critic report).

### Task 6: Matcher

**Files:** Create `backend/intake/match.py`. Test `backend/tests/test_intake_match.py` (uses the `embed` fixture and `fake_vector` from `tests/conftest.py`).

**Interfaces:**
- Consumes: profiles (Task 3), `search.models.SchemaEmbedding`, `search.embedder.embed`, `duplicates.service._engine`, `schema.introspect`.
- Produces:
  - `fingerprint(headers: list[str]) -> str`.
  - `match(schema: str, sources: list[Source], profiles: list[dict], row_match: bool) -> dict`, returning `{"recipe": {"id", "mapping", "filters"} | None, "searchOffline": bool, "sources": {name: {"tables": [[table, score]] (best 3), "columns": {header: [[table, column, score]] (best 3)}, "refs": {header: {"table", "key"}}, "rows": {"table", "exists": [{"row": int, "id": int}], "maybe": [{"row": int, "id": int, "score": float, "existing": str}], "examples": [...] (≤20)}}}}`.
  - Column texts are `"<header> (<type>): <samples joined by ', '>"`, embedded as `query` and compared by cosine with `kind="column"` rows of the schema. With `SearchError` → difflib name similarity and `searchOffline=True`.
  - Table score = the sum of the best column scores that land in that table.
  - Refs: a column where ≥ 90% of distinct sample values equal a parent's unique text column (read with `ro_connection`, at most 2,000 values per parent).
  - Rows: an exact match on the target's single-column unique key → `exists`. Otherwise `_engine().find_duplicates` over existing rows (default name fields, at most 50,000 rows read) plus incoming rows, keeping cross pairs only → `maybe`.

  - an exact business key → `exists`;
  - `Acme Co., Ltd.` vs stored `Acme Company Limited` → `maybe`, not `exists`;

### Task 7: Designer, Critic and the run

**Files:** Create `backend/intake/design.py`, `backend/intake/run.py`, `backend/intake/management/commands/run_import.py`, `backend/intake/signals.py` (wired in `apps.py`). Test `backend/tests/test_intake_run.py`.

**Interfaces:**
- Consumes: Tasks 1–6, `chat.providers.complete(provider, messages, [], model, key=)`, `chat.errors.ChatError`, `scripts.storage.save`, `scripts.validate.validate`, `scripts.service.submit`, `settings_app` rules text (as the `get_rules` MCP tool builds it).
- Produces in `design.py`:
  - `ask(prompt, profiles, matches, rules_text, targets_text, answers, feedback, api_key) -> dict`, returning `{"mapping", "filters", "reasons": {path: str}, "questions": [str] (≤3)}`.
  - The system message demands one JSON object of that shape. The reply is parsed with code fences stripped. A parse failure gets one retry with the error; a second → `DesignError("the model did not return a valid plan")`.
  - The model is `import.model or chat.defaultModel`; none → `DesignError("no chat model is configured")`.
- Produces in `run.py`:
  - `start(user, upload_id, schema, prompt, api_key="") -> ImportRun`. Refuses when the user already has an open run for this schema. It calls `uploads.complete_raw` and spawns `manage.py run_import <id>`, passing the key through the environment variable `SINGULARITY_IMPORT_KEY`, never through the DB.
  - `execute(run_id, api_key="")` is the body of the command. It heartbeats like `scripts.jobs`, moves through the states, and writes one `ImportMessage` per role turn:
    - profiler: a summary line per sheet;
    - matcher: the top table per sheet, how many rows already exist or may, and whether search is offline;
    - designer: its decisions in a few lines, or its questions;
    - critic: "passed" with counts, or the problems.
  - Designer ↔ Critic loop, at most `maxRounds`:
    - the Critic calls `script.write` + `storage.save` + `validate.validate(script, mapping, schema)`;
    - `report["ok"]` → `ready`;
    - otherwise its errors (gate, orphans, rows, mapping issues; at most 20, each ≤300 chars) are the next round's `feedback`;
    - out of rounds → `failed`, with the last problems in the thread.
  - Questions → `waiting_for_answer`. `answer(user, run_id, text)` stores the answer, adds a `person` message, and resumes at `designing`.
  - `recheck(user, run_id, mapping, filters, skip)`: the person's edits. Runs the Critic only, then `ready` or `failed`.
  - `submit(user, run_id, note) -> Change`: regenerates the script from the final plan and validates it once more (refuses if not ok), then calls `scripts.service.submit`. Sets `change`, state `submitted`.
  - `signals.py`: on `Change` post_save with status APPLIED, find the ImportRun with `change=instance`, and upsert the `ImportRecipe` for (schema, fingerprint) with its mapping and filters.
  - A stale heartbeat (600 s) reads as `failed`. Runs past `expires_at` are purged with their files (add them to the existing purge command).

  - `test_bad_designer_output_never_ready`: non-JSON twice → `failed` with the reason; a mapping to an unknown column → the critic feedback appears in the round-2 prompt; three bad rounds → `failed`.
  - `test_questions_pause_and_resume`.
  - `test_recipe_drift_is_repaired`: the recipe maps to a dropped column → the thread reports drift, and the round-1 prompt contains it.
  - `test_recheck_after_edit_skips_designer`.
  - `test_submit_creates_one_pending_change`, including that skipped and filtered rows are not in the stored script.
  - `test_recipe_saved_when_applied` (approve the change with `approvals.service.approve`).
  - `test_one_open_run_per_user_and_schema`; `test_api_key_not_stored` (searched in every JSON field and message).
