# Smart script upload (web) - design

## Problem

A person dropped a 248 MB pg_dump (about 192,000 rows, about 80 tables) into the Scripts tab and could not go on: the Validate button stayed disabled. Three causes sit behind that:

1. **Size.** nginx accepts 60 MB on `/api/scripts` and the app caps a script at `limits.maxScriptBytes` (50 MB). The upload fails, no script exists, `Validate` stays disabled, and the only hint is one small error line.
2. **Unsupported SQL stops the file.** `\restrict` lines and the pg_dump 18 `SET` lines already parse. But real dumps also carry `CREATE EXTENSION`, `CREATE SEQUENCE`, `ALTER SEQUENCE ... OWNED BY`, `nextval(...)` defaults, `GRANT`, functions and triggers. Each one is a hard error today (checked with a pg_dump 18 style sample), and one error stops the whole file.
3. **Manual steps.** Upload, then Validate, then an optional mapping, then Submit. Nothing happens by itself, and the page shows raw errors instead of handling what it can.

## Goal

Choose a file, and the page does the rest: it uploads (any size up to a configured cap), reads, auto-maps and validates by itself, and then shows "Ready: N tables, M rows" with one Submit button. What cannot be imported is listed with a reason instead of blocking. Real errors stay errors, with a plain-language fix.

## Out of scope

- Importing functions, triggers, extensions, sequences, grants or ownership (skipped and reported, never executed).
- Upsert/update loads, a CLI or API-token upload, changes to the gate rules or the approval flow.
- The MCP tools (staged loads, PR #40) and the `submit_script` tool. The parser change is shared, so `submit_script` and `validate_script` benefit too.
- The nightly worker (piece 4). Validation jobs are started by the API, not by the worker.

## Design

### 1. Tolerant parser (`scripts/sqlparse.py`)

Statements are sorted into three classes instead of two:

- **Imported** (as today): CREATE TABLE, ALTER TABLE ... constraints, indexes, comments, views, enums, COPY and INSERT rows.
- **Skipped with a reason** (new): listed in the report as `skipped: [{line, statement, reason}]` and shown to the person under "Not imported, and why". They do not make the report fail.
  - `CREATE EXTENSION`, `COMMENT ON EXTENSION`: "extensions are managed by the server".
  - `CREATE SEQUENCE`, `ALTER SEQUENCE ...`, `SELECT setval(...)`: "ids are generated by the loaded table itself".
  - `ALTER COLUMN ... SET DEFAULT nextval(...)` and a `DEFAULT nextval(...)` inside CREATE TABLE: the default is dropped, the column keeps its identity or key. (Reported once per column.)
  - `GRANT`, `REVOKE`, `ALTER DEFAULT PRIVILEGES`, `ALTER ... OWNER TO` forms not already ignored: "permissions are set by the server".
  - `CREATE FUNCTION/PROCEDURE`, `CREATE TRIGGER`, `CREATE RULE`, `CREATE POLICY`: "logic that cannot pass the rules gate was not imported" (these are the ones to warn about loudly: they get their own warning block).
- **Errors** (as today): anything that could change data or schema in a way the gate cannot check (DROP, DELETE, UPDATE, TRUNCATE, unknown statements, a syntax error). The message says what to do (for example "remove this statement from the file or move it into a separate script").

The skipped statements are detected from the pglast parse tree (statement kind), never by text matching. A skipped statement that spans lines (a `$$` function body) is cut by the same statement splitter that already handles `$$`.

`ParsedScript` gains `skipped: list[ScriptIssue-like]`; `validate` copies it into `report["skipped"]` (capped like `ignored`, with a count of the rest).

### 2. Big uploads (chunked, streamed to disk)

New endpoints under `/api/scripts/uploads` (editor only, same CSRF rules):

- `POST /api/scripts/uploads` with `{name, size}` creates an upload session and returns `{upload_id, chunk_bytes, max_bytes}`. Refused up front with a plain message when `size` exceeds `limits.maxScriptBytes`.
- `PUT /api/scripts/uploads/<id>/<n>` sends chunk `n` (raw body, up to `chunk_bytes`, default 8 MiB); the server writes it to `SCRIPT_DIR/uploads/<id>.part` at offset `n * chunk_bytes`, so a resent chunk overwrites itself (resume after a dropped connection is "ask `GET`, send what is missing").
- `GET /api/scripts/uploads/<id>` returns `{received: [n...], size}` for resume.
- `POST /api/scripts/uploads/<id>/complete` checks every chunk arrived, then streams the part file into the normal script storage in one pass (BOM strip, UTF-8 check, NUL check, CRLF to LF, sha256, size) without holding the file in memory, and returns the same `{script_id, sha256, size}` as today.

The old single-request `POST /api/scripts` (file or JSON paste) keeps working for small files. `limits.maxScriptBytes` default rises to 512 MiB (tunable range raised to match); nginx gets `client_max_body_size 16m` on `/api/scripts/uploads` (chunks are 8 MiB) and the old 60 MB `location` stays for the small path. Unfinished upload sessions expire after 24 hours and their part files are purged by the same expiry routine style as scripts.

### 3. Validation as a background job

A 248 MB parse cannot run inside one web request (proxy and worker timeouts). `POST /api/scripts/<id>/validate` gains `?async=1`: it records `report = {"state": "running", "progress": {...}}`, starts `python manage.py validate_script <id> [--schema ...]` as a separate process (the API does not wait), and returns `202`. `GET /api/scripts/<id>` already returns the stored report, so the page polls it every 2 seconds; progress is "Reading", "Parsing", "Checking rows", "Dry run", written by the command at each phase. The synchronous path stays for small scripts and for the MCP tools.

The command is the same `validate` function as today. A crashed or killed process leaves `state: "running"` forever, so `GET` treats a running job with no progress update for 10 minutes as "failed: the check stopped unexpectedly, try again". One running job per script.

`storage.read` and `validate._run` currently hold the whole file as `bytes` and `str`. The plan starts by measuring a synthetic 250 MB dump (80 tables, 192,000 rows) in a test and sets the memory approach from the result: the COPY row streams are already lazy, so the likely change is to parse the file with the statement splitter reading line by line rather than decoding the whole text at once. The acceptance criterion is a 250 MB synthetic dump validated end to end in a test run within the container memory limit, not a particular technique.

### 4. One-click page (`frontend/components/ScriptsTab.tsx`)

- The page states the size limit before a file is chosen ("up to 512 MB").
- Choosing a file starts: upload (progress bar, resume on failure), then validate with the suggested mapping, automatically. A paste box stays for small SQL.
- Phases show as one list: Uploading 63%, Reading, Checking rows, Dry run, Ready.
- Result: "Ready: 80 tables, 192,000 rows" with a Submit button; below it, collapsed groups: "Not imported, and why" (skipped) and "Notes" (ignored boilerplate).
- Real problems show as plain sentences with the line number and a fix, not raw parser text; the raw text stays in a "Details" fold.
- The destination picker and the mapping JSON move under "Customize (optional)". Changing either re-runs validation.
- The tab keeps showing the person's last script after a failed upload, and Validate stays enabled for it. A failed upload shows an error with the reason (too large, connection lost, not UTF-8) and a "Try again" button.

## Errors and edge cases

- A file over the cap: refused before any byte is sent, with the cap and the file size in the message.
- A connection that drops mid-upload: the page asks `GET` and resumes; after three failed attempts it shows "Try again".
- Two tabs uploading the same file: two independent sessions; fine.
- A chunk sent after `complete` or after expiry: refused with `410`.
- A non-UTF-8 or NUL-containing file: refused at `complete` with the same messages as today.
- A script that only has skipped statements and no data: "Nothing to import" (an error, not "Ready").

## Testing

- Parser: one test per skipped class and one for each kept error class; the pg_dump 18 sample from this design as a fixture; a `nextval` default in CREATE TABLE and in ALTER COLUMN; a `$$` function skipped whole.
- Upload: chunks in order, out of order, a resent chunk, a missing chunk at `complete`, over the cap, expiry, a non-editor, CRLF and BOM handling equal to the single-request path (same sha256).
- Job: start, poll, phase text, completed report equals the synchronous report, a killed process becomes a failed state, one job per script.
- Scale (marked `slow`): 250 MB synthetic dump through chunked upload and background validation.
- Frontend (vitest): choosing a file runs upload then validate with no further click; Validate stays enabled after a failed upload; skipped statements render under "Not imported"; resume path; the customize fold re-runs validation.

## Resolved decisions

- **Functions, triggers and similar:** skip with a loud warning, never block (decided with the owner).
- **Where validation runs:** a process started by the API (the worker container is still a placeholder).
- **Cap:** 512 MiB by default, tunable.
